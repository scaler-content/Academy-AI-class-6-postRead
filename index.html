    01

    Where we are: you wrote this in Python already

    Something comes in, a model processes it, something goes out. You wrote that in Python, in four files. Now you build the same shape without writing code, and you add the parts your app never had: it runs on its own, and it sends the result somewhere.

    Map · Python to n8nSelect a pair
    Important

    n8n is not a different kind of AI. The node that calls the model is making the same API call you made in Class 1, with the same three roles and the same key. What n8n gives you is everything around that call: a trigger, branching, connections to other services, and a picture of what happened.

    Think of something you do manually every week that could run on its own. The best of those ideas becomes your own build in Section 9.

    02

    The canvas: triggers, nodes, connections

    Three ideas, and then you can read any workflow you ever meet.

    IdeaWhat it is
    TriggerWhat starts the workflow. A form, a schedule, an incoming message, or you pressing a button.
    NodeOne step. Call a model, send an email, add a row, make a decision.
    ConnectionThe line between two nodes. Data flows left to right along it.

    That is the whole mental model. Everything else is which node you picked.

    How data moves

    Every node hands the next node a list of items, and each item is JSON. Class 2 taught you to ask a model for JSON; this is where that pays off, because the next node can reach into it by field name. A node does its job once per item: hand it five tickets and it runs five times.

    Simulator · Items on the canvasChange how many tickets arrive

    Items leaving the trigger (each is JSON):

    Important

    When something does not work, the question is almost always "what did this node actually receive". Not what you think it received. n8n shows you, and Section 7 is about reading it.

    03

    Getting n8n running, and importing a workflow

    Before class

    Watch the n8n install walkthrough video and complete the install. It is the step-by-step for installing n8n on your own machine and getting it running. It takes about fifteen minutes and almost all of that is waiting for things to download.

    The checkpoint

      If your local install will not start

      Use n8n Cloud at n8n.io instead and keep going. Everything in this class works the same there, with one exception that Section 4 names. Do not spend time debugging an install; sort it out afterwards.

      Importing a workflow

      Two ways in, and both are worth knowing.

      From a file

      Open the workflow menu, the three dots at the top right of the canvas, and choose Import from File. Pick a .json and the whole workflow appears.

      From the clipboard

      Copy workflow JSON as text, click anywhere on the canvas, and paste. n8n reads JSON on the clipboard and draws the nodes. If you fall behind during a build, this is the rescue: paste a shared JSON instead of rebuilding.

      04

      The node types you need, and how credentials work

      You will meet hundreds of nodes. They are all one of five things.

      Trigger

      Starts the workflow.

      Form, Schedule, Webhook, Manual

      AI

      Calls a model.

      OpenAI Chat Model and the other chat model nodes

      Action

      Does something in another service.

      Gmail, Google Sheets, Telegram

      Logic

      Decides or reshapes.

      IF, Switch, Edit Fields

      HTTP Request

      Calls any API with no dedicated node.

      The escape hatch

      Try it · Which kind of node?Quick drill
      Important

      HTTP Request is the one to remember. If a service has no n8n node but has an API, you can still use it. That single node is the difference between "n8n cannot do that" and "n8n can do anything with an API".

      Credentials: connect once, reuse everywhere

      Any node that touches an outside service needs credentials. You create them once and every workflow can use them. There are two kinds and they cost very different amounts of your time.

      Compare · API key vs OAuthSelect a credential
        The one exception worth knowing

        Google nodes such as Gmail and Sheets use OAuth, and on a self-hosted n8n you have to register your own application with Google to get a client ID and secret first. On n8n Cloud that is handled for you. It is not hard, it is just a detour, so do it before class rather than during it.

        Why can a self-hosted install not borrow n8n's OAuth app? The redirect has to come back to your machine.

        The AI node, and the swappable brain again

        The chat model node needs a credential too. You can point an OpenAI-type credential at a different provider by changing the base URL, exactly as you did in first_call.py.

        Same key, same base URL, same model name as the code you wrote in Class 1. The brain is swappable here too, and for the same reason: the interface is the same.

          05

          Live build: support ticket triage

          A ticket arrives, the model reads it and decides how urgent it is and what it is about, and then urgent and routine tickets go to different places.

          The shape
          Form  ->  AI classifies  ->  IF urgent?  ->  yes: Telegram alert
                                         ->  no:  Gmail draft reply
          Stepper · Build it node by nodeBuild the first branch before the second

          The system prompt

          It should look familiar, because it is Class 2's structured output lesson.

          System prompt
          You triage incoming customer support tickets.

Return only JSON with exactly these keys:
{
  "category": "delivery | billing | product_fault | other",
  "urgency": "high | normal",
  "sentiment": "angry | neutral | happy",
  "summary": "one sentence, under 20 words",
  "suggested_reply": "a polite reply, under 80 words, no promises about refunds"
}

Mark urgency high only if the customer mentions a deadline, a legal threat,
or says they have already been ignored.

Return only the JSON object. No explanation, no code fences.
          Important

          That last line is the one from Class 2, and it matters more here than it did in a chat window, because the next node is going to try to read these fields by name. A friendly sentence before the JSON breaks the whole workflow.

          Simulator · Route a ticketA rule-based stand-in for the model
          AI node output (JSON)
          What the branch does

          A simple keyword rule stands in for the model here, following the prompt's own urgency rule: a deadline, a legal threat, or already being ignored. A real model reads the ticket properly and can disagree. Submit an angry ticket with a deadline, then a calm one, and the two go down different branches.

          Important

          You have just built something a real support team would recognise: a triage step that reads unstructured text, makes a judgement, and routes accordingly. The only thing missing for production is error handling, which is Class 8.

          If Gmail OAuth is not working, put a second Telegram node on the false branch with a different message. The lesson is the branch, not the mail provider.

          06

          Expressions: the prompt template with variables

          So far every node used fixed text. Expressions are how a node uses the data flowing into it. This is the template prompting that Classes 2 and 3 deferred: it needs real variable injection to be worth teaching.

          The syntax

          An expression is wrapped in double curly braces and reads from $json, which is the item coming in.

          ExpressionWhat it gives you
          {{ $json.urgency }}The urgency field from the previous node
          {{ $json.customer_email }}The email the customer typed into the form
          {{ $json.summary.toUpperCase() }}The summary, shouted. It is JavaScript inside the braces
          {{ $('Form Trigger').item.json.subject }}A field from a specific earlier node, not just the previous one

          That last row is the one people need and do not know to look for. Once you are three nodes deep, the thing you want is often not from the node immediately behind you.

          The template, finally

          Prompt template
          A customer wrote in about an order. Write a reply.

Their name: {{ $json.customer_name }}
Their order number: {{ $json.order_id }}
What they said: {{ $json.message }}
How urgent we judged it: {{ $json.urgency }}

Match the tone to the urgency. Do not promise a refund.

          The prompt is written once. The values change on every run. That is the difference between a prompt you paste and a prompt that is part of a system.

          Visualizer · Expression resolverMini evaluator for $json and named nodes

          The node directly before this one is:

          $json (the current input)
          Also available by name
          Resolved preview
          Important

          The resolved preview is the whole trick. You can see what an expression evaluates to before you run anything, so a typo in a field name is obvious immediately rather than three runs later. In n8n, drag a field from the input panel into a text box and it writes the expression for you; learn to drag first and the syntax second.

          Is this the same as the few-shot examples from Class 2? Common doubt

          No, and they combine well. Few-shot is examples of the output you want, written into the prompt. This is injecting live data into a prompt. A production prompt usually has both: fixed rules, fixed examples, and variable slots for whatever just came in.

          07

          Reading a run, and breaking it on purpose

          When a workflow misbehaves, you do not guess. Every node keeps what went in and what came out.

          The loop

          1. Run the workflow and look at the canvas. Nodes that ran are marked, and the one that failed is marked differently.
          2. Click the failing node. You get two panels: input on the left, output on the right.
          3. Read the input. The question is always the same: is this what you expected this node to receive?
          4. If yes, the node's own settings are wrong. If no, the problem is upstream: move one node to the left and repeat.
          Try it · The debugging questionAnswer it for the node you are inspecting

          Is the input what you expected this node to receive?

          Pick an answer.
          Important

          That is the entire debugging method and it works on every workflow you will ever open, including somebody else's. Most workflow problems are a field name that does not exist, and the input panel shows you that in two seconds.

          Break it on purpose

          These are engineered failures, so they reproduce every time, whatever the model does.

          08

          Export, import, and sharing your work

          A workflow is a JSON file. Knowing that is what lets you back it up, share it, move it between machines, and put it in version control.

          Visualizer · What is in the fileSimplified illustration
          
        
          
      
          
    
          
  
          
  
          Exporting
          
  
            
  
            Important
            Your credentials are not in that file. n8n exports a reference to a credential, not the key itself. That is what makes it safe to share a workflow, and it is also why importing someone else's workflow means reconnecting your own accounts before it runs.
            
  
            Importing
            
  
            From a file (the same three-dot menu, then Import from File) or from the clipboard (copy the JSON and paste it onto the canvas, the fastest way to share one in a chat). Then reconnect credentials: any node that needs an account will show that it needs one.
            
  
            Why this matters beyond backups
            
  
            In Class 4 you learned that the instructions are yours and the platform's box is temporary. The same applies here. A workflow you can export is a workflow you own. You can diff two versions, you can keep it in a repository, and you can move it to a different n8n without rebuilding it by hand. Export today's workflow and keep the file: you will want it next class.

  10
  
            Wrap-up and what is next
            
  
            What you can do now
            
  
            
    
            Read any workflow
            As triggers, nodes and connections, and say what data is moving along each line.
            
    
            Connect a model
            Using the same key and the same base URL as your Python code.
            
    
            Inject live data
            Into a prompt with expressions: the template prompting deferred to this class.
            
    
            Debug by reading
            What a node actually received, rather than guessing.
            
  
            
  
            And you can export a workflow as JSON, which means you own it.
            
  
            What is still missing
            
  
            Today's workflow has no error handling. If Telegram is down, the run fails and nobody finds out. If the model returns something unexpected, the branch does the wrong thing silently. Real automations need retries, fallbacks and a way to tell somebody when they break.
